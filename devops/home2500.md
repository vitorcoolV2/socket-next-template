# Home2500 Ecosystem Overview

The Home2500 stack is a self-hosted infrastructure designed for security, automation, and centralized management. This document describes the core ecosystem components and the role of the master blueprint.

## 🏗️ Core Infrastructure Requirements

The system relies on a tightly coupled set of core services:

1. **Identity (Authentik)**: The central IAM (Identity and Access Management).
2. **Edge Proxy (Traefik)**: Handles TLS termination and routing, integrated with Authentik for Forward Auth.
3. **DNS (Pi-hole)**: Internal name resolution for the `<service>.$DOMAIN` naming convention.
4. **Secrets (Vault/KeePass)**: Secure storage and runtime secret injection.

## 📜 The Master Blueprint (`core-home2500.yaml`)

The file `devops/authentik/blueprints/core-home2500.yaml` acts as the **Configuration Anchor** for the entire ecosystem. It defines the state of the infrastructure within Authentik.

### 1. Identity Structure (Groups)

Defines the project's user hierarchy:

- `Home-Admins`: Full access to infrastructure tools (Traefik, Pi-hole, Vault).
- `Home-Developers`: Access to development tools and non-critical infra.
- `Home-Users`: Basic access to end-user applications (e.g., Whoami).

### 2. Infrastructure Services (Providers)

Registers the core services that require protection:

- **Pi-hole**: Internal DNS dashboard.
- **Traefik**: Edge router dashboard.
- **MailCrab**: Internal mail testing tool.
- **Vault SSO Gate**: Protection layer for the Vault UI to prevent bypass.

### 3. Application Definitions

Maps the providers to UI-friendly applications in the Authentik Dashboard, including:

- **Launch URLs**: Redirects to the proper HTTPS endpoints.
- **Icons**: Standardized branding across the portal.
- **Policy Bindings**: Enforces group-based access (e.g., `group-admins` only for Pi-hole).

### 4. Outpost Synchronization

Ensures the **Embedded Outpost** is aware of all registered services. This allows Traefik to communicate with Authentik to validate tokens at the edge.

## 📂 Directory Relationships

The `devops/` directory is structured to reflect the dependencies defined in the blueprint:

| Directory        | Relation to Blueprint | Core Responsibility                                                               |
| :--------------- | :-------------------- | :-------------------------------------------------------------------------------- |
| **`authentik/`** | **Orchestrator**      | Hosts the blueprint and applies it to the running instance.                       |
| **`traefik/`**   | **Enforcer**          | Uses the `ProxyProviders` defined in the blueprint for Forward Auth.              |
| **`pihole/`**    | **Service**           | Its dashboard is registered as an `Application` in the blueprint.                 |
| **`vault/`**     | **Service**           | Integrated via the SSO Gate defined in the blueprint.                             |
| **`app/`**       | **Extension**         | Contains the `tool.sh` framework to onboard new apps not in the master blueprint. |

## 🚀 Extending the Core Ecosystem (Custom Apps)

Beyond the core infrastructure, the stack is designed to be easily extended with custom services (e.g., `backup/`, `fotos/`, `opencode/`). These apps reside in their own folders within `devops/` and follow a standardized integration pattern.

### 1. The Integration Framework (`tool.sh`)

Custom apps leverage the **App Framework** located at `devops/authentik/app/tool.sh`. This library provides the heavy lifting for:

- Database provisioning (Postgres).
- Secret mapping (Vault/KeePass).
- DNS registration (Pi-hole).
- SSO/OIDC integration (Authentik Blueprints).
- Proxying (Traefik/Outposts).

### 2. The App Entrypoint (`init.sh`)

Every custom app typically contains an `init.sh` script that acts as the controller. A standard `init.sh` follows this pattern:

```bash
#!/bin/bash
# Path: devops/<app_name>/init.sh

# 1. Source the Framework
source ../authentik/app/tool.sh

# 2. Define the Deploy Function
deploy() {
    # Standard deployment workflow
    tool_stages_workflow
}

# 3. Handle specific stage failures (optional)
on_provision_db_fail() {
    echo "Check Postgres container health..."
    return 1
}
```

### 3. Standardized Stages (`tool_stages_workflow`)

When `deploy` is called, the framework executes the `tool_stages_workflow`, which runs through a predefined sequence of stages:

| Stage                   | Action                                              |
| :---------------------- | :-------------------------------------------------- |
| **`script`**            | Validates the integrity of the local `init.sh`.     |
| **`provision_db`**      | Creates DB and roles if `APP_DB_NAME` is in `.env`. |
| **`provision_secrets`** | Maps global secrets to the app context.             |
| **`vault_login`**       | Ensures Vault session is active.                    |
| **`compose`**           | Injects secrets and runs `docker compose up -d`.    |
| **`running`**           | Verifies container availability and IP assignment.  |
| **`name_register`**     | Syncs internal and public DNS in Pi-hole.           |
| **`authentik_login`**   | Validates Authentik API access.                     |
| **`blue_apply`**        | Compiles and applies OIDC/Proxy blueprints.         |

### 4. Why use `tool_stages_workflow`?

This workflow ensures that every app in the Home2500 ecosystem is deployed with the same security and connectivity standards. It abstracts away the complexity of managing DNS, TLS, and SSO, allowing you to focus on the service itself.

## 🛠️ Global Requirements

For the ecosystem to function, the following must be consistent across all modules:

- **`DOMAIN`**: All services and blueprint URLs assume a common domain (default: `home2500.local`).
- **`INTERNAL_DOMAIN`**: Docker-internal networking (`.app-network`).
- **`AUTHENTIK_API_TOKEN`**: Required to apply the blueprint changes to the server.
- **`VAULT_CACERT`**: Essential for secure OIDC handshakes between Vault and Authentik.
